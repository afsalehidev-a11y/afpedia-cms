# تحلیل فنی و برنامهٔ تطبیق مهاجرت C# به PHP/Laravel

**مخزن:** `afsalehidev-a11y/afpedia-cms`  
**شاخه:** `migration/php-laravel-final`  
**وضعیت سند:** نسخهٔ کاری؛ مبنای ادامهٔ مهاجرت و پذیرش فنی  
**اصل راهنما:** تا زمانی که قابلیت‌های موجود C# با رفتار معادل در PHP پیاده‌سازی و با آزمون قابل تکرار تأیید نشده‌اند، قابلیت جدیدی از backlog شروع نمی‌شود.

## 1) هدف و معیار پایان

هدف، بازنویسی ظاهری یا صرفاً عبور CI نیست؛ هدف حفظ رفتار قابل مشاهدهٔ محصول C# در پیاده‌سازی PHP/Laravel است. هر قابلیت زمانی «تکمیل» محسوب می‌شود که:

1. رفتار و قواعد نسخهٔ C# مشخص و به مرجع کد/آزمون متصل باشد.
2. پیاده‌سازی PHP متناظر وجود داشته باشد.
3. آزمون واحد/یکپارچهٔ معادل، سناریوی موفق و ناموفق را پوشش دهد.
4. آزمون روی نسخه‌های پشتیبانی‌شدهٔ PHP و در موارد وابسته به DB روی موتور واقعی هدف اجرا شود.
5. مهاجرت داده، امنیت، خطاها و سازگاری نصب مستند و بررسی شده باشند.

عبور workflow به‌تنهایی اثبات parity کامل نیست.

## 2) مبنای بررسی

در این دور، فایل‌های زیر از شاخهٔ PHP خوانده شدند:

- `app/Http/Controllers/Auth/AuthenticatedSessionController.php`
- `app/Support/Identity/AspNetIdentityPasswordHasher.php`
- `app/Models/User.php`
- `config/auth.php` و `config/session.php`
- `tests/Feature/AuthenticationTest.php`
- ساختار migrationها و فایل‌های مرتبط با identity

برای مرجع C#، فایل‌های زیر از شاخهٔ `main` خوانده شدند؛ در شاخهٔ مهاجرت PHP این مسیرهای C# وجود ندارند:

- `src/AFPedia.CMS.Domain/Identity/UserAccount.cs`
- `src/AFPedia.CMS.Infrastructure/Identity/CmsUser.cs`
- `src/AFPedia.CMS.Infrastructure/Identity/CmsRoleSeeder.cs`
- `src/AFPedia.CMS.Infrastructure/Identity/CmsAuthorizationPolicies.cs`

بنابراین در مواردی که نیازمند بررسی controller، تنظیمات Identity یا تست‌های C# است، این سند نتیجهٔ قطعی اعلام نمی‌کند و آن‌ها را در فهرست بررسی بعدی نگه می‌دارد.

## 3) وضعیت فعلی Identity

| حوزه | آنچه در کد فعلی دیده شد | ارزیابی فعلی |
|---|---|---|
| مدل دامنهٔ کاربر | C# دارای Guid، Email، DisplayName، Role، IsActive و CreatedAtUtc است؛ PHP مدل دامنه و تست‌های قبلی دارد | تطبیق جزئی؛ آزمون موردی لازم |
| DisplayName | C# متن خالی/فاصله‌ای را رد و Trim می‌کند؛ محدودیت 160 در PHP اضافه شده است | محدودیت طول تست شده؛ رفتار Trim/ورودی whitespace باید cross-check شود |
| نقش‌ها | C# seeder نقش‌های تعریف‌شده را در صورت نبود ایجاد می‌کند؛ PHP seeder اکنون شناسهٔ نقش موجود را حفظ می‌کند | تست regression حفظ شناسه و عضویت در CI سبز شده |
| مجوزها | C# نام policyهای ManagerOnly و ContentEditors را تعریف می‌کند؛ PHP متدهای isManager/canEditContent دارد | منطق و تمام نقاط مصرف باید مقایسه شوند |
| ورود | PHP ایمیل را trim و lowercase می‌کند، کاربر غیرفعال/قفل‌شده را رد می‌کند و session را regenerate می‌کند | تست‌های پایه وجود دارد؛ rate limit و تطبیق normalization هنوز نیازمند تأیید |
| قفل حساب | PHP پس از 5 تلاش ناموفق، 15 دقیقه قفل می‌کند؛ موفقیت شمارنده و lockout را پاک می‌کند | سناریوهای اصلی تست شده؛ رفتار مرزی و concurrency نیازمند تست بیشتر |
| هش رمز | verifier برای ASP.NET Identity V2/V3 وجود دارد و پس از ورود موفق hash قدیمی به Laravel منتقل می‌شود | مسیر اصلی تست شده؛ تست برداری از hash واقعی C# لازم است |
| نشست | نام cookie، Secure، HttpOnly، SameSite=Lax، path=/ و lifetime=480 دقیقه در config دیده شد | با سیاست C# گزارش‌شده هم‌راستا؛ آزمون HTTP واقعی و proxy/HTTPS لازم |
| دادهٔ قدیمی | migration سازگاری ستون‌های Identity و backfill نقش‌ها وجود دارد؛ created_at_utc nullable باقی مانده | تست runtime روی MySQL/MariaDB و سناریوی دادهٔ قدیمی لازم |

## 4) اختلاف‌ها و ریسک‌های مشخص برای پیگیری

### 4.1 محدودسازی نرخ تلاش ورود
بررسی تکمیلی route و AppServiceProvider نشان داد مسیر POST ورود از `throttle:login` استفاده می‌کند و limiter با سقف 10 تلاش در 15 دقیقه و کلید ترکیبی ایمیل lowercase + IP تعریف شده است. بنابراین این تنظیم در PHP وجود دارد؛ بااین‌حال تست اختصاصی برای اثبات کلید ترکیبی، مرز 10/15 دقیقه و رفتار cache store هنوز باید اضافه شود و با مرجع C# مقایسه گردد.

### 4.2 استفاده از normalized_email
controller کاربر را با `where('email', $email)` جست‌وجو می‌کند، درحالی‌که schema ستون `normalized_email` دارد. باید روشن شود تمام مسیرهای ایجاد/ویرایش کاربر این ستون را همواره و با قاعدهٔ واحد پر می‌کنند یا نه. سپس تصمیم بر اساس قرارداد C# گرفته شود؛ تغییر کورکورانهٔ query پیش از شناخت داده‌های موجود ممنوع است.

### 4.3 رفتار قفل و تراکنش
در PHP خواندن کاربر با `lockForUpdate()` داخل transaction انجام می‌شود. باید روی MySQL/MariaDB واقعی تست شود؛ SQLite رفتار قفل‌گذاری معادل ارائه نمی‌کند. تست هم‌زمانی تلاش‌های ناموفق برای جلوگیری از عبور از سقف نیز لازم است.

### 4.4 سازگاری رمز عبور
verifier فعلی ساختارهای V2 و V3 را می‌خواند. آزمون فعلی V3 با پارامترهای تولیدشده در PHP ساخته شده است؛ این آزمون به‌تنهایی اثبات سازگاری byte-for-byte با خروجی واقعی ASP.NET نیست. باید fixture ثابت تولیدشده توسط ASP.NET Identity (بدون افشای رمز واقعی کاربر) به تست افزوده شود؛ همچنین PRFهای SHA1/SHA256/SHA512، طول‌های نامعتبر و ورودی خراب بررسی شوند.

### 4.5 تاریخ ایجاد UTC
ستون `created_at_utc` در migration سازگاری nullable است. تبدیل خودکار `created_at` به UTC بدون دانستن timezone تاریخی داده‌ها خطرناک است. فعلاً fallback موجود در repository باید حفظ شود؛ هر backfill فقط پس از اثبات timezone منبع و داشتن تست دادهٔ نمونه انجام شود.

### 4.6 نقش قدیمی و عضویت
تغییرات اخیر seeder و migration برای حفظ شناسه‌ها و عضویت‌های موجود انجام شده‌اند و تست CI مربوط به seeder سبز است. migration backfill باید جداگانه با fixture شامل نقش موجود با UUID غیرپیش‌فرض، کاربر با نقش معتبر، نقش نامعتبر و اجرای دوبارهٔ migration بررسی شود.

## 5) برنامهٔ اجرایی به ترتیب

### مرحله A — تکمیل نقشهٔ مرجع C#
- فهرست controllerها، endpointها، application serviceها، domain entityها، policyها، migrationها و تست‌های C# استخراج شود.
- برای هر رفتار، فایل و تست مرجع ثبت شود.
- مواردی که در C# تست ندارند با برچسب «نیازمند تصمیم/مشخصات» مشخص شوند؛ حدس جای قرارداد را نمی‌گیرد.

### مرحله B — ماتریس قابلیت به قابلیت
برای هر قابلیت این ستون‌ها تکمیل شوند: نام قابلیت، مرجع C#، پیاده‌سازی PHP، آزمون PHP، داده/مهاجرت، امنیت، نتیجه و لینک CI. وضعیت‌ها فقط «تأییدشده»، «در حال انجام»، «مسدود/نامشخص» باشند.

### مرحله C — بستن شکاف‌های Identity
به ترتیب:
1. بررسی route/middleware برای rate limit و افزودن تست ترکیب email+IP.
2. بررسی تمام مسیرهای نوشتن email و normalized_email.
3. تطبیق policyها و نقاط استفادهٔ مجوزها.
4. افزودن fixture واقعی ASP.NET برای hash V2/V3 و تست upgrade.
5. تست lockout، concurrency، inactive، lockout expiry و reset.
6. بررسی cookie/session روی HTTPS و پس از logout.

### مرحله D — مهاجرت و DB
- اجرای migrationها روی MySQL 8 و MariaDB 10.6 (یا نسخهٔ دقیق پشتیبانی‌شده).
- آزمون اجرای fresh install، upgrade از schema قدیمی، اجرای مجدد seed، حفظ UUID و membership، rollback ایمن و داده‌های ناقص.
- SQLite فقط برای تست سریع است و جای DB هدف را نمی‌گیرد.

### مرحله E — تثبیت build و نصب
- تعیین نسخه‌های دقیق PHP/Laravel و dependencyها.
- ایجاد و commit کردن `composer.lock` از طریق Composer واقعی؛ فایل lock نباید دستی یا حدسی ساخته شود.
- آزمون release bundle شامل vendor dependencies، نصب‌کنندهٔ مرورگری، نبود نیاز مشتری به SSH/Composer و بررسی shared hosting در محیط‌های واقعی.
- آزمون backup/restore و مجزا بودن داده/فایل/تنظیمات هر نصب.

### مرحله F — پذیرش parity
هر ردیف ماتریس باید آزمون سبز و شواهد داشته باشد. سپس مرور امنیتی، نصب fresh و upgrade، و smoke test end-to-end انجام می‌شود. تنها پس از بسته‌شدن این موارد، backlog جدید باز می‌شود.

## 7) قواعد تصمیم‌گیری

- هیچ قابلیت موجودی صرفاً به دلیل نبودن تست در PHP حذف یا ساده‌سازی نمی‌شود.
- هیچ رفتار نامشخصی از روی حدس پیاده‌سازی نمی‌شود؛ ابتدا مرجع C# یا تصمیم محصول ثبت می‌شود.
- تغییر schema باید migration برگشت‌پذیر/ایمن و تست داده داشته باشد؛ rollback نباید دادهٔ دسترسی را ناخواسته حذف کند.
- تست‌های واحد، feature، DB واقعی و end-to-end مکمل هم هستند.
- CI سبز یک شرط لازم است، نه معیار نهایی پذیرش.
- تغییرات کوچک، مستقل و قابل بازبینی commit می‌شوند.

## 8) خروجی‌های مورد انتظار

1. ماتریس کامل C# → PHP با وضعیت هر قابلیت.
2. مجموعهٔ تست‌های parity و regression.
3. گزارش نتایج MySQL/MariaDB و نسخه‌های PHP.
4. composer.lock و release bundle قابل نصب.
5. راهنمای نصب، ارتقا، backup/restore و محدودیت‌های محیط میزبانی.
6. گزارش نهایی موارد تأییدشده، موارد باقیمانده و ریسک‌های پذیرفته‌شده.
